M1 Silicon Overview: Three Processors, One Memory

Lesson 2 · AIRobot · LLM Inference at the Metal Level

The M1 is not "a CPU with a GPU." It's a heterogeneous SoC: three radically different processors connected by one memory bus.

In Lesson 1, you learned that every LLM operation reduces to tensor primitives: dot, matmul, softmax, elementwise ops. In AIRobot, all of these run on the CPU via Java's Vector API — which compiles to ARM NEON SIMD instructions.

But your MacBook Air has three processors, not one. Each is built for a different kind of math. This lesson maps each tensor operation to the processor that would execute it best, and explains why AIRobot uses only one of them.

The M1: Three Computers on One Die

CPU

~200 GFLOPS

4+4 cores. NEON SIMD (128-bit). Serial-control-heavy. Low latency per operation.

Your code runs here.

GPU

2.6 TFLOPS

7–8 cores, 1024 ALU. SIMT (warp parallelism). High throughput, high launch latency.

You'd use Metal to reach it.

ANE

11 TOPS

16 cores. Systolic array for matmul/conv. Max efficiency, opaque API.

Only Core ML can touch it.

All three share the same LPDDR4X memory at 68.25 GB/s. There is no PCIe bottleneck, no buffer copy, no VRAM limit separate from system RAM. The unified memory architecture is the M1's superpower for inference: a model too large for a discrete GPU's VRAM doesn't hit a hard wall — it just gets slower as the CPU/GPU share bandwidth.

Trace a matmul Through Each Processor

Take a single forward-pass matmul: wq · xb, where wq is (dim=4096 × dim=4096) and xb is (dim=4096).

StepCPU (NEON)GPU (Metal)
Launch call matmul() → loop over rows encode 4096 threads → submit command buffer → GPU scheduler dispatches
Latency ~microseconds (function call overhead) ~10–50 µs (kernel launch + synchronization)
Execution 1 row at a time, 4 FMAs per NEON instruction × 4 P-cores = 16 flops/cycle 1024 threads in flight simultaneously, each computing one row's dot product
Memory pattern Sequential cache-line reads (12 MB L2 fits one weight row) Wide scatter-gather across DRAM; tile memory reduces pressure
Wins when Small batches, irregular shapes, quantized formats Large batches, big matmuls, high arithmetic intensity

Batch size matters. At batch=1 (autoregressive), the GPU spends more time launching kernels than computing. At batch=32, the GPU's 1024 ALUs eat the matmul for breakfast.

Why AIRobot Is CPU-Only

Open FloatTensor.java at the line that reads:

// (Apple Silicon) NEON only supports up-to 128bit vectors.
static final int VECTOR_BIT_SIZE = ...

Your code already knows it's on Apple Silicon. It's using the Java Vector API (jdk.incubator.vector) which the JVM compiles to NEON fmla (fused multiply-add) instructions. That's the fastest way to do dense linear algebra on the CPU without dropping down to C.

To reach the GPU, you would need:

  1. JNI (Java Native Interface) — bridge Java → C/Swift
  2. Metal compute shaders — write matmul and softmax kernels in the Metal Shading Language
  3. Buffer management — wrap FloatTensor's storage as MTLBuffer for zero-copy access in UMA

To reach the ANE, you would need to rewrite the model as a Core ML model — which means losing AIRobot's tensor interface entirely. The ANE has no public API; it is only accessible through Core ML's private frameworks.

Key insight: The M1's GPU is 10× more FLOPs than the CPU, but AIRobot can't reach it without a native bridge. This is a software boundary, not a hardware one. The unified memory means there's no data-movement penalty — the only cost is language/runtime friction.

Check Your Understanding

Question 1

Why does the GPU's massive parallelism advantage shrink at batch size 1 in autoregressive decoding?

Answer: Kernel launch latency dominates. The GPU needs ~10-50 µs to dispatch a compute kernel, but the matmul for one token's attention scores is tiny (1 × seq_len). The CPU finishes the same work in a few microseconds of direct function calls — no dispatch overhead.

The GPU only wins when the matmul is large enough (batch × dim) to amortize the launch cost across enough ALUs.

Question 2

Open FloatTensor.java:64. The comment says "NEON only supports up-to 128bit vectors." How many float32 operations does one NEON instruction do per cycle?

Answer: 4. A 128-bit vector holds 4 × float32 values. A NEON fmla (fused multiply-add) performs 4 multiply-adds = 8 flops per instruction. With 4 P-cores, that's 32 flops/cycle theoretical peak.

Compare to the GPU: 1024 ALUs at ~1.3 GHz = 2.6 TFLOPS. The GPU's ALUs are simpler (no branch prediction, no out-of-order), so they pack more per mm² at lower power.

Question 3

What architectural feature makes the M1 uniquely suited for running LLMs that exceed a discrete GPU's VRAM?

Answer: Unified memory. A discrete GPU with 16 GB VRAM cannot load a 32 GB model at all — it must offload layers to system RAM over PCIe (~20-32 GB/s). On the M1, the CPU and GPU both access the same 16 GB pool. The tradeoff is bandwidth: a 32 GB model doesn't fit in 16 GB either, but the difference is that every processor on the M1 shares the same memory bottleneck, whereas a discrete GPU hits a hard VRAM wall.

Practically: M1 Max/M2 Ultra with 64-192 GB can hold large models entirely in unified memory, which no consumer discrete GPU can match.
