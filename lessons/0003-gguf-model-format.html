GGUF Model Format

Lesson 3 · AIRobot · LLM Inference at the Metal Level

Your Mac's gguf file is a very close cousin of the ZIP format — it bundles metadata, tensors, and their quantized layouts into one self-describing container. FloatTensor never sees a container; it sees a tensor entry from the GGUF and loads the referenced data directly to its decompressor.

In AIRobot's GGUF.java, ModelLoader parses the file at runtime and creates Weights — which are just FloatTensor instances mapped by layer and role. This happens the first time you run forward() — LLama3.java line 52 calls it, so the cost is paid on first inference.

  1. File magic (first 4 bytes: GGUF) identifies it as a GGUF container.
  2. Header (version + metadata key-value pairs) describes tensors and quantization types.
  3. Tensor entries — one per weight matrix: name, shape, quantization, byte offset.
  4. Aligned weight data — raw bytes, padded to 32-byte boundaries.

GGUF vs ZIP Analogy

GGUF Magic: 0x46554747 ("GGUF") Header: version (uint32) └ key-value pairs → tensor descriptors └ "general.architecture" → "llama" └ "general.file_type" → 1 (sequential) Tensor Entry: name (string), dimension (uint32[]), quantization (enum), offset (uint64) └ "blocks.layer.wq.weight" └ "blocks.layer.wk.weight" └ "blocks.layer.wv.weight" └ "output.weight" └ weight data (aligned to 32 bytes)

The GGUF container is exactly like a ZIP with no compression but 4-byte alignment for tensors. It lists everything and where to find it — no external index, no filesystem scanning.

Key Sections

Weight Data Raw bytes (packed Q4_0, Q8_0, BF16, F16, F32) FloatTensor constructors (see Q4_0FloatTensor(byte[] slice))\n\n

Quantization Types in GGUF

by Type: GGMLType enum (see src/com/llama4j/GGMLType.java) F32, F16, BF16, Q8_0, Q4_0, Q2_K, Q3_K, Q4_K, Q5_K, Q6_K └CPU: Q8_0 (int8 + fp32 scale), Q4_0 (int4 + fp32 scale) └GPU: F16 (native), FP32 (scalar fallback) └ANE: not supported by Core ML (FP16/INT8 only)

GGUF is agnostic to the quantized format. The container just says "blocks.0.wq.weight" → Q4_0, offset=1024, shape=[4096,4096]. Each FloatTensor subclass knows how to parse its own slice of the data.

Tensor Loading

TRACE through FloatTensor.java matmul line 63: First it computes dot(i * dim1, that, 0, dim1) → that.getFloat loops reading from the tensor's storage. For a Q4_0FloatTensor, getFloat decompresses the block (see Q4_0FloatTensor.java:88). Weight data is never decompressed as a whole — the block iterators (NEON) read from the slice directly.

Model Loading Steps

  1. ModelLoader.loadModel(ggufPath) opens file, reads magic.
  2. Parses header → Configuration (contextLength, numberOfLayers, dim, vocabSize) + weights offset table.
  3. For each tensor entry, allocates a FloatTensor according to quantization type (ArrayFloatTensor for F32/F16, Q4_0FloatTensor for Q4_0, etc.)
  4. Reads slice from FileChannel at offset into tensor's ByteBuffer (see Q4_0FloatTensor:74 memorySegment setup)
  5. Caller (Llama.createNewState) can now matmul or dot directly without copying.

File Map vs. Memory Layout

CPU OrderGPU OrderApple Silicon Advantage
Sequential (default GGUF) → load via FileChannel.open(modelPath, READ) Trivial (UMA) → same DRAM, zero-copy CPU FloatVector accesses block data directly from file-backed ByteBuffer (no CPU copy)
Split-by-layer (e.g., Q6_K) → complex interleave logic (not AIRobot) Tile memory → no CPU offload, tensors fit in DRAM Tensor data stays in DRAM when used by NEON, avoiding extra memcpy

Currently AIRobot expects a **sequential GGUF** (row-major tensors) — equivalent to typical matmul(W, X) memory access pattern.

Hints for Users

  • GGUF validation — Quick check: head -c 4 model.gguf | hexdump -e '/1 "%02X"' | head -n 1 should print 47 47 55 46
  • Layer order — Look at metadata general.architecture (LLaMA, LLaMA2, etc.)
  • Quantization — Check general.file_type field for Q format (more Q20 = smaller file, more decompression overhead)
  • Tensor inspection — Use jnew inside FGrep: GGUF → dump only name and quantization lines.
