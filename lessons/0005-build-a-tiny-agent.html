Build a Tiny Java Agent

Lesson 5 · AIRobot · LLM Inference at the Metal Level

You already understand the engine: tokens in, logits out, a sampled next token. This lesson adds the smallest possible thing on top of it — a loop that lets the model act on the world and read back what happened.

You have built an inference engine. This lesson turns it into an agent: a system that can do something and use the result. The whole agent is about 60 lines of Java, and it reuses Llama.generateTokens exactly as it is.

The gap a lone LLM cannot cross

An LLM predicts the next token from its weights and the text in its context. It has no senses. Ask it today's date and it will produce a fluent, confident, wrong answer, because the date is nowhere in its weights and nowhere in the prompt. The same is true of "what is in this directory" — the model cannot look.

We validated exactly this while building the lesson: asked to reply with the token stream TOOL: date, the 1B model instead answered December 8, 2006. It guessed. That guess is the problem an agent solves.

The agent loop

An agent wraps the engine in a loop: think → act → observe → repeat → answer.

          question
             |
             v
   +--------------------+        no TOOL line
   |  build prompt      |---------------------------> final answer
   |  (question +       |
   |   observations)    |
   +--------------------+
             |
             v
   +--------------------+     TOOL: <cmd>
   |  llm.generate()    |--------------------> validate & run command
   +--------------------+                              |
             ^                                         v
             |                              append "OBSERVATION: ..."
             +-----------------------------------------+
                        repeat (max 5 steps)
  1. Think — build the prompt: the question plus any observations so far.
  2. Act — the model replies. If the reply contains TOOL: <cmd>, that is the action.
  3. Observe — run the command and append OBSERVATION: <output>.
  4. Repeat — regenerate with the observation in context, up to 5 steps.
  5. Answer — any reply with no TOOL: line is the final answer.

Key idea: the model never "knows" the date. It knows how to ask for it. The loop supplies the knowledge from the real world.

The loop lives in src/com/llama4j/AgentLoop.java. The engine call is the same Llama.generateTokens(...) you met in Lesson 4 (Llama.java:342).

Walk the loop

1. The protocol. The model needs to be told the grammar. With a 1B model the instruction must be brutally short — every extra line made it refuse or invent an answer:

You can run commands. To get the date reply with TOOL: date

That is the entire system prompt. The allowlist — date, ls, pwd, whoami, echo — is not here. It lives in code, so a weak or even adversarial prompt cannot widen what the agent may run.

2. Parsing the action. A single regex extracts the command from the generated text. It is anchored to the start of a line, so a passing mention of TOOL: mid-sentence does not fire. If there is no match, the model has finished:

static final Pattern TOOL_PATTERN =
        Pattern.compile("(?m)^[ \\t]*TOOL:[ \\t]*(\\S[^\\r\\n]*)", Pattern.CASE_INSENSITIVE);

3. Running the tool, safely. The command is split into arguments and executed without a shell. That is why ls; rm -rf / cannot sneak a second command past the allowlist — ls; is not a program name:

String[] parts = cmd.trim().split("\\s+");
if (!ALLOWED.contains(parts[0])) {
    return "error: command not allowed: " + parts[0];
}
Process process = new ProcessBuilder(parts).redirectErrorStream(true).start();

4. The loop. Generate, parse, run, append, repeat — with a hard cap so a stubborn model cannot loop forever:

for (int step = 0; step < MAX_STEPS; step++) {
    String reply = llm.generate(buildContent(question, observations));
    Optional<String> toolCall = parseToolCall(reply);
    if (toolCall.isEmpty()) {
        return reply.strip();          // no action -> final answer
    }
    observations.add(runShell(toolCall.get()));
}

Small models do not always stop on their own. Once an observation exists, the prompt builder appends a one-line cue so the model finally answers instead of calling the tool again:

if (!observations.isEmpty()) {
    builder.append("\nFinal answer:");
}

5. The seam. The loop never mentions Llama. It depends on one method — Llm.generate(String) — which is why it is testable with a fake model and reusable with the real one:

public interface Llm {
    String generate(String userContent);
}

The wiring

src/com/llama4j/MiniAgent.java connects the loop to the engine: it owns the Llama model, a ChatFormat, the KV cache state, and the growing token list. It also prints a small trace so you can watch the loop work. The bridge is one method reference:

public String answer(String question) {
    return new AgentLoop(this::generate).answer(question);
}

this::generate runs the same token pipeline you already built: encode the prompt, call Llama.generateTokens with Sampler.ARGMAX, decode the new tokens, and hand the text back to the loop.

Check your understanding

Question 1

After the agent receives an observation, what happens next?

Answer: It adds the observation and generates another reply.

Question 2

Why does the tool run commands without invoking a shell?

Answer: No shell means pipes and semicolons cannot run.

Question 3

What stops the loop when the model never emits a final answer?

Answer: The five step limit forces one final answer.
