Tokenization — The First Step

Lesson 4 · AIRobot · LLM Inference at the Metal Level

Tokenization is the interface where your intent enters the model as integers that flow through tensor pipelines. Every token ID sets off the embedding lookup, making tokenization the de facto "entry point" in forward-pass mechanics.

The first operation in AIRobot's forward pass is converting raw text into indices that index into the token_embedding_table — `FloatTensor.copyTo(token_id × dim, x, 0, dim)`.

What does AIRobot's tokenizer do in forward-pass flow

  1. Preprocess the input string → trim whitespace, append <|begin_of_text|> if empty
  2. Apply pre-tokenization → split on word boundaries, subword regex
  3. BPE merge → recombine most frequent char pairs (based on tiktoken vocabulary)
  4. Lookup BPE merges in Vocabulary.java → integer token IDs (0-128k)
  5. Embed to tensor → token_embedding_table.copyTo, fills x for RMSNorm

The key player: Tokenizer.encode

File: `src/com/llama4j/Tokenizer.java`, method encode(String text) returns `List tokenIds`. 

// Llama3.java:51
String prompt = in != null ? in.getValue() : "hello";
List tokenIds = tokenizer.encode(prompt);
// tokenIds = [123, 456, 789, ...] (sequence of token IDs)

// Pass IDs into tensor via Llama.createNewState
Llama model = Llama.loadModel(path);
State state = model.createNewState(tokenIds);
FloatTensor xb = state.x;  // already embedded

AIRobot's tokenizer implementation strategy

AIRobot uses Tiktoken BPE — same as OpenAI's models — but with LLaMA-specific customizations:

ComponentValue
VOCAB_SIZE128256 tokens
BOS_TOKEN<|begin_of_text|> → 0
EOS_TOKEN<|eot_id|> → 128257
MERGE_FILEBytePair merges trained on RedPajama dataset
TOKENIZER_TYPETiktoken (BPE with RoPE pattern)

What matters for **metal-level** knowledge: the tokenizer produces an array of integers that drive tensor operations. The encoding logic itself is secondary to understanding how token IDs become tensor indices.

TRACE: Tokenization → embedding in forward-pass

Open `Llama.createNewState` and follow token_id → tensor flow:

1. Input string: "Hello world"
2. Tokenize: ["<|begin_of_text|>", "Hello", "world", "<|eot_id|>"]
3. IDs: [0, 1024, 2048, 128257]
4. Embedding lookup in createNewState
   token_embedding_table.copyTo(0, state.x, 0, dim)      // token 0 at position 0
   token_embedding_table.copyTo(1024, state.x, 1, dim)  // token 1024 at position 1
   ...
5. Result: state.x is FloatTensor of size nTokens×dim

Every matmul in the layer uses indices derived from these same token IDs — for positional encoding, attention masking, etc.

Category mapping — Token object (concept) ↔ ID (concrete)

The token abstraction layer (`Vocabulary.java`) is what bridges raw text to tensor storage. It can be thought of as the token's passport to the embedding table.

// Vocabulary.get("Hello") returns Integer 1024 in HashMap
// Tokenization produces Integer[1024]
// Embedding lookup: token_embedding_table.getFloat(1024 * dim + i) // i from 0 to dim-1

Tokenizer tuning notes

Tokenizer tuning affects the **user experience** (text coverage, whitespace) more than the **tensor layer** (the embedding lookup stays the same). However, a poorly designed tokenizer can cause intermittent embedding issues, especially for languages outside your training set.
